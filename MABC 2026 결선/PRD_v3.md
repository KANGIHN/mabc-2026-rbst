# PRD_v3 — 갈피(ResumeCard): 개업 변호사 대상 사건 재개 카드 서비스

> 이 PRD는 skill-to-service 미니 PRD(에이전트에게 주는 설계도)다.
> work-resume(예선 제출 스킬)을 기반으로 Vercel에 독립 배포하는 웹 서비스 MVP의 설계도.
> 타겟을 개업 변호사(송무 중심 개인·소형 법률사무소)로 재정의한 v3.
> 공백·미확정은 "확인 필요"로 표시한다.

---

## 0. 호출 대상 스킬 및 안전 점검 결과 (skill-to-service A-0 반영)

| 점검 항목 | 내용 |
|---|---|
| 스킬명 | work-resume (업무 재개 카드) |
| 예선 제출 여부 | 본인 예선 제출 스킬 (확인 완료) |
| 목적 | 흩어진 사건 기록을 재정리해 "이어가고 싶은 사건 하나"에 대한 재개 카드(현재 상태 → 첫 행동 → 주의사항 + 근거) 생성 |
| 데이터 출처 | ① 사용자 직접 입력(질문형/사건번호형 + 선택 메모) ② 연결 환경 시 Timely 앱 커넥터(메일·캘린더·메모 등) ③ 외부 기록 없을 때 서비스 내부 대화/기록 참고(보조, 실제 환경 확인 필요) ④ 데모 모드용 예시 데이터 |
| 필요한 설정 | 서비스 런타임 LLM = Solar Pro 4 (API 키: Vercel 환경변수, 이름만 PRD 8번에 기재, 값은 등록 시 사용자가 직접 입력) |
| 외부 전송 | /api 서버리스 함수가 Solar Pro 4 API만 호출. 그 외 외부 주소로는 요청하지 않음. 클라이언트(index.html)에는 키·프록시 주소 0개 |
| 권한 요구 | 셸 실행·파일 시스템 접근·다른 계정/토큰 요구 없음 |
| 안전 점검 결과 | 통과 — 호출 대상 스킬로 사용 가능 |

**이 스킬만으로는 할 수 없는 일 3가지 (PRD 범위 설정에 반영)**
1. 연결된 MCP 도구(메일·캘린더·메모)가 없는 환경에서 실제 외부 사건 기록을 대신 가져오지 못함 → 보충 입력/데모 경로로 대체
2. 사용자 계정·저장값이 없는 첫 방문에서 이전 맥락(지난 재개 이력 등)을 복원하지 못함 → 이번 MVP는 1건 재개 카드 생성이 중심
3. 토스·인계용 별도 포맷, 교대·인수인계 템플릿, 히스토리 누적 관리는 이번 MVP 범위에서 제외

## 1) 한 줄 정의
개업 변호사가 "이어가고 싶은 사건 하나(사건번호/질문)"만 입력하면, 흩어진 사건 기록(메일·메신저·초안·사무장 메일·캘린더 등)을 다시 훑지 않고도 **사건 재개 카드(사건번호/사건명/다음 기일 + 현재 상태 → 첫 행동 → 주의사항 + 근거)** 1장을 바로 받아서 다음 행동으로 이어갈 수 있게 하는 웹 서비스.

---

## 2) 타깃 사용자 (WHO)

- **구체적인 한 사람**: 송무를 주로 다루는 개업 변호사(개인·소형 법률사무소). 준비서면 제출 주기·기일 간격 1~3주 단위로 한 사건을 몇 주 만에 다시 집어드는 일이 일상인 사용자.
- **상황 예시**:
  - 연휴·휴가 복귀 후 밀린 사건 재개
  - 다른 사건 진행 중 잠시 놓았던 사건 다시 열기
  - 사무장/의뢰인에게 토스받은 사건 맥락을 빠르게 파악
  - 변론기일·항소기간 등 시간이 흐르는 사건 우선순위 확인
- **접근성·언어**: 한국어 인터페이스, 별도 계정 없이 URL로 접속, 사무실 PC에서 전자소송을 상시 열어두는 환경이라 웹 접근 장벽 낮음.
- **선정 근거**:
  - 재개가 업무의 기본 형태(준비서면 제출 주기·기일 간격 1~3주)
  - 대형 로펌은 사건관리시스템·기록 정리 인원 별도 보유, 개업 변호사는 그 자리가 비어 있고 도구 도입을 본인이 결정 → 타겟 유리
- **주의**: "없으면 치명적"(놓친 기록·기한 → 고객 패소, 금전/명예 리스크)은 타겟 선정 근거로만 사용하고, 제출물 문구에서는 톤 조절.

---

## 3) 문제

- **재개 마찰**: 몇 주 만에 다시 집어드는 사건이 일상이고, 다시 열 때마다 흩어진 맥락을 다시 조립하는 부담이 큼.
- **흩어진 현재 위치**: 사건 공식 상태는 전자소송에 있지만, 재개할 때 실제로 필요한 건 메일/메신저/초안/사무장 메일/캘린더 등에 흩어져 있어 "내가 어디서 끊었는지"를 바로 알기 어려움.
- **방향 혼재 리스크**: 서로 다른 방향 기록이 공존할 때(예: 의뢰인 합의 의향 vs 준비서면 전액 다툼) 무엇이 현재 방침인지 확인 부담이 크고, 추정/요약으로 한쪽을 골라주는 방식은 이 직군에서 오히려 위험.
- **직접 입력방식으로 해결 불가한 부분**:
  - 사용자가 기록할 곳을 기억해서 매번 찾아 넣어야 함 → 번거로움
  - 기록이 여러 곳에 쌓이면 어느 것이 최신인지 판단이 어려워짐
  - 최신 기록을 못 믿으면 재사용하지 않게 됨 → 결국 서비스를 안 쓰게 됨
- **그래서**: 서비스는 "이어가고 싶은 사건 하나"만 묻고, 그 단서로 연결된 도구·MCP에서 관련 기록을 스스로 찾아 모으는 구조. 사용자는 기록을 찾아다니지 않고, 결과(카드)만 확인.

## 4) 트리거 (WHEN)

- 사용자가 URL로 들어와 직접 입력하는 **온디맨드 호출형** 서비스.
- 트리거 순간 예시:
  - 출근·휴가 복귀 직후 밀린 사건 정리
  - 프로젝트 전환보다는 "한 사건을 몇 주 만에 다시 집어드는" 순간
  - 사무장/의뢰인에게 토스받은 사건 맥락을 바로 파악할 때
  - 변론기일·항소기간 등 시간이 흐르고 있어 우선순위 확인이 필요할 때
- 서비스가 먼저 가야 하는 방식(공유 링크·알림)은 이번 MVP 범위에서 제외.

## 5) 핵심 기능

### P0 (결선 데모 필수, 최대 4개)

1. **입력 접수**: "이어가고 싶은 사건 하나"를 질문형 또는 사건번호형으로 입력. 필요하면 최근 한 줄 메모·기록 요약·토스 맥락 단서(선택) 첨부.
   - placeholder: "이어가고 싶은 사건을 질문이나 사건번호로 알려줘"
   - 예시 노출(시간 특정 표현 제외): "2026가단12345 손해배상 — 합의/서면 방향", "2026가단67890 임대차 — 원상복구비 반박", "2026나54321 공사대금 항소 — 우선 확인"

2. **서비스 주도 처리 (기록 탐색 로직 + 충돌·대기·확인 필요 처리 + 다중 사건 상한)**: 입력된 단서로 서비스 로직이 관련 항목을 정리. 연결 환경에서는 **Timely 앱 커넥터(Gmail, Google Calendar, Google Docs, Google Sheets, Google Drive 등) 중 사용자가 선별한 도구**로 관련 기록을 탐색. MVP 우선 반영 대상은 **Google 관련 5개**로 하고, 나머지는 사용자 선별에 따라 확장. 미연결/심사 환경이면 사용자가 입력한 메모·키워드·보충 텍스트를 기준으로 처리하고, **테스트용·심사용 데모/보충 경로를 별도로 확보**해 핵심 로직이 실제 돌아가는 흐름이 보이게 함. (실제 각 커넥터가 제공하는 기능·도구 범위는 연결/연동 시 확인 필요)

3. **사건 재개 카드 출력**: 카드 1장 — 사건번호/사건명/다음 기일(D-n 형태) 상단 → 현재 상태(라벨) → 첫 행동 1개 + 근거 1줄 → 주의사항(기한/리스크/대기/충돌/확인 필요) → 근거 펼침/접기(핵심 1줄 우선, 펼치면 상세). 다중 사건이 식별되면 우선 사건 카드 1장만 출력하고 나머지는 요약·목록("그 외 ○○건 더 있어요")으로 안내.

4. **체험(데모) 경로(가상 데이터 기반, 선택형 예시 체험)**: 연결된 도구·MCP 연동 환경이 아니어도 핵심 흐름(입력 → 처리 상태 표시 → 카드 출력, 상태 판정 → 첫 행동 → 주의사항 + 근거, 충돌 처리)이 실제로 진행되는 흐름을 예시로 보여줌. 단순 정적 예시 카드 노출이 아니라 **실제 로직이 돌아가는 구조**. 데모 데이터는 가상 사건 3건 × 각 사건 관련 기록 4~5건으로 구성, 각 기록의 상태는 충돌/대기/완료 등으로 다양하게 배치.
   - **데모 진입 방식**: '데모 예시로 체험하기' 선택 시 예시 사건 3건이 칩(버튼) 목록으로 보이고, 그중 하나를 골라 해당 사건의 가상 기록 4~5건으로 카드 생성 흐름을 체험. 필요하면 다른 예시 사건도 선택 가능.
   - **예시 표지**: "데모 예시" 문구를 기본으로 하고, 필요 시 "업스테이지 MABC 2026 대회 맥락 예시" 정도로 보충. 실제 사건명/맥락 명칭은 예시 사건의 구체적 이름으로 채움.

### P1 (있으면 좋지만 당장 아닌 것)

- 태그/키워드 입력 보조(자동 추천 제외), P0-1에 자연스럽게 녹아 있는 수준으로만.
- 결과 화면 UX 다듬기(근거 펼침/접기, 핵심 근거 우선 노출 등).
- 진입 문구("완벽하게 재개할 필요 없이, 5분만 이어서 보기")를 필요한 곳에 얇게 사용.
- "그 외 ○○건 더 있음" + "다른 업무 보기" 연결점(다중 사건 식별 시).

## 7) 입력·출력

### 입력

- **메인 입력**: 짧은 텍스트 1개(질문형 또는 사건번호형). placeholder + 예시 문구 2~3개 노출.
  - placeholder: "이어가고 싶은 사건을 질문이나 사건번호로 알려줘"
  - 예시: "2026가단12345 손해배상 — 합의/서면 방향", "2026가단67890 임대차 — 원상복구비 반박", "2026나54321 공사대금 항소 — 우선 확인"
- **선택 입력(얇게)**: 최근 한 줄 메모·기록 요약·토스 맥락 단서(보충용, 필수 아님).
- **보조 UI**: "데모 예시로 체험하기" 칩/버튼(입력창 근처, 작게, 보조 위치). 사건번호 포함 입력 시 자동 데모 라우팅.

### 출력

- **기본**: 사건 재개 카드 1장
  - 사건번호/사건명/다음 기일(D-n 형태) 상단
  - 현재 상태(라벨 가능: 진행 중/대기/확인 필요/확인 필요(기록 충돌)/완료 등)
  - 첫 행동 1개 + 근거 1줄
  - 주의사항(기한/리스크/대기/충돌/확인 필요)
  - 근거 펼침/접기(핵심 1줄 기본, 펼치면 상세 근거)
- **충돌/확인 필요**: 그대로 표시, 하나로 덮지 않음
- **다중 사건**: 우선 카드 1장 + 그 외 요약·목록("그 외 ○○건 더 있어요")
- **처리 중 상태 표시**: "기록을 찾고 있어요…" 문구 + progress bar, 버튼 비활성화
- **기록이 없을 때**: "연결된 도구에서 관련 기록을 찾지 못했어요." + 보충 입력/데모 제안 (중립·도움 톤)
- **작업 실패**: "기록을 불러오는 중 문제가 있었어요. 잠시 후 다시 시도해 주세요." (기록 없음과 구분)

## 8) 필요 설정

### 8-1. 배포 연결 (Vercel 커넥터)
- Vercel에 배포. 값 취급 없음(설정 존재만 확인).

### 8-2. 서비스 키 (Vercel 환경변수)

| 이름 | 용도 | 발급처 | 값 |
|---|---|---|---|
| SOLAR_API_KEY | /api에서 Solar Pro 4 호출 시 인증용 | 대회 제공 크레딧/키 | (등록 시 사용자가 직접 입력, 대화에 값 적지 않음) |

- 위 표에 있는 이름만 Vercel 환경변수로 등록. 표에 없는 변수는 등록하지 않음.
- **Google 앱 커넥터(Gmail, Google Calendar, Google Docs, Google Sheets, Google Drive) 등 외부 서비스 인증은 Vercel 환경변수에 키를 하드코딩하지 않는다.** 커넥터별 인증은 Timely 연결/OAuth 등 Timely가 정한 방식으로 처리하며, 소스코드·배포물·PRD·서비스 UI에 인증정보를 노출하지 않는다(제9조 제6항).
- 환경변수는 /api 서버리스 함수만 읽음. 클라이언트(index.html)에는 키·프록시 주소 0개.

### 8-3. 사용자 프로필 (웹 화면 입력 → localStorage)

- MVP에서는 계정 없이 사용. 사용자별로 저장할 프로필은 이번 MVP에서 최소화.
- 입력 예시·최근 입력 등 편의성 저장만 localStorage로 가능(재방문 시 묻지 않음, 초기화 버튼 제공).
- 민감 정보 저장 금지.

## 9) 데이터 규칙

- **출처·기준 시각 표기**: 카드 내 근거에 "어떤 입력/기록을 근거로 했는지" 범위를 표시. 데모 모드면 "데모 예시" 표지.
- **없는 값**: '확인 불가'로 표시(추정 금지).
- **추정**: 합리적으로 추정할 수 있는 경우에만 [추정] 태그로 명시. 근거 없는 과추정 금지. 확정적 종료 표현만 완료로 판정("완료", "다 했", "끝났다", "더 할 일 없음" 등). "거의 끝남", "마무리 예정" 등은 진행 중/확인 필요로 처리.
- **키·프록시 주소는 서버(/api)에만. 클라이언트에 0개.**
- **최소 권한**: /api는 Solar Pro 4 API와 데모 데이터만 접근.
- **외부 데이터 활용 시 저작권·출처 표기 준수, 타인 저작물·동의 없는 개인정보 포함 금지.** 특히 **Gmail·Google Drive 등 개인정보가 포함될 수 있는 커넥터 자료**를 활용하는 경우, 업무상 필요한 개인 특정 정보(이름·연락처·메일주소) 범위만 표시하고 나머지는 출력 제외 + "민감정보로 출력하지 않음" 명시. 민감정보는 **저장하지 않음**(localStorage 등 포함).
- **개인정보 처리**: 입력은 요청 단위로만 처리, 서버에 저장하지 않음. 심사 응답 및 PRD 문구 준비 필수.

## 10) 성공 기준 (데모 시나리오 + 시크릿 창 테스트)

### 데모 시나리오 (P0 검증용)

1. **질문형 입력 → 카드 1장 출력**: "2026가단12345 손해배상 — 합의/서면 방향" 입력 → 사건번호/사건명/다음 기일(D-n) 상단, 현재 상태(확인 필요·기록 충돌), 첫 행동 + 근거, 주의사항, 근거 펼침 확인
2. **사건번호형 입력 → 자동 데모 라우팅**: "2026가단67890 임대차보증금" 입력 → 자동 데모 경로 연결 → 카드 출력
3. **기록 없음 상황**: 연결된 도구에서 관련 기록 없음 → 보충/데모 제안 안내 (중립·도움 톤)
4. **데모 예시 체험**: 칩 클릭 → 예시 표지("데모 예시")와 함께 실제 로직 흐름(처리 상태 표시 → 카드 출력) 확인
5. **충돌 상황 데모**: "확인 필요(기록 충돌)" + 첫 행동이 "무엇을 어디서 확인/행동할지" 형식으로 제시(의뢰인에게 합의 의사 확인 후 서면 방향 결정)
6. **다중 사건 데모**: 우선 카드 1장 + "그 외 ○○건 더 있어요" 요약·목록

### 시크릿 창 테스트 (필수)

- 저장값·계정 없는 브라우저(시크릿 창)로 첫 방문했을 때:
  - 서비스명("갈피 - ResumeCard") + 한 줄 설명 + 입력 필드 + 예시 문구 + 카드 생성 버튼이 스스로 보임
  - "데모 예시로 체험하기" 칩/버튼이 보조 위치로 보임
  - 최소 기능(입력 → 카드 출력)이 동작하는지 확인
  - /api 응답 JSON에 환경변수 값이 섞여 있지 않은지 확인
