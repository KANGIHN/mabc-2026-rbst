## 배경: 왜 이 작업을 하는가

멘토링 피드백 반영: 기존 타겟("하던 일이 끊겼다 다시 시작하는 모든 직장인")이 너무 넓고, 문제가 얕아서 수요가 불확실함. 타겟을 좁히고 페인포인트와 제공 가치를 재정의해서 기획을 다시 잡음.

---

## 1. 변경된 기획 (확정)

### 타겟
- 기존: "하던 일이 끊겼다 다시 시작하는 모든 직장인"
- 변경: **개업 변호사 — 송무 중심의 개인, 소형 법률사무소**
- 선정 근거:
  - 재개가 업무의 기본 형태 (준비서면 제출 주기·기일 간격 1~3주, 한 사건을 몇 주 만에 다시 집어드는 일이 매일)
  - 사무실 PC에서 전자소송을 상시 열어두고 일하므로 웹 서비스 접근 장벽 낮음
  - 대형 로펌은 사건관리시스템·기록 정리 인원 별도, 개업 변호사는 그 자리가 비어 있고 도구 도입을 본인이 결정 → 타겟 유리
- 주의:
  - "없으면 치명적"은 타겟 선정 근거로만 사용, 제출물 문구는 톤 조절
  - 경험 기반이 아니라 자료조사 기반 — 확정 아닌 건 확인 필요로 분리
  - 서비스는 법전 판단·결론 대행 아님. 변호사가 업무 관련 "다음으로 할 일"을 보여주는 것

### 페인포인트 (3층)
1. **재개 마찰**: 몇 주 만에 다시 집어드는 사건이 일상이고, 다시 열 때마다 흩어진 맥락을 다시 조립하는 부담
2. **흩어진 현재 위치**: 사건 공식 상태는 전자소송에 있지만, 재개할 때 필요한 건 메일/메신저/초안/사무장 메일/캘린더 등에 흩어져 있어 "내가 어디서 끊었는지"를 바로 알기 어려움
3. **방향 혼재 리스크**: 서로 다른 방향 기록이 공존할 때 무엇이 현재 방침인지 확인 부담, 추정/요약으로 한쪽을 골라주는 방식은 이 직군에서 오히려 위험

### 서비스가 제공하는 것
- **한 사건 = 업무 재개 카드 1장**
- 카드 구성:
  - 현재 상태 (있는 조각만 기준, 추정 없이)
  - 지금 할 첫 행동 1개
  - 그 행동의 근거
  - 주의사항 (기한/대기/충돌 등)
  - 출처·조각 (판단에 쓴 원문 조각을 그대로 남김)
- 차별점:
  1. 검색 요약 도구는 기록 보여주기에서 끝나지만, 이 서비스는 상태 판정 + 다음 행동 1개 지정까지 함
  2. 기록이 어긋나면 한쪽을 고르지 않고 둘 다 보여준 뒤 "확인 필요"로 판정, 무엇을 어디서 확인할지 제시
  3. 판단 결과만이 아니라 그 판단의 출처를 함께 보여줌 (신뢰 → 반복 사용)
- 원칙: 사실 기반, 추정 안 함. RAG 유사 개념 — 있는 정보만 답변, 근거와 출처 남김

## 3. MVP 수정 범위 (확정)

### ✅ 넣는 것
1. **데모 데이터 교체**: 변호사 사건 3건, 사건당 기록 4~5건 이하, 기존 데모 전부 폐기
2. **카드 헤더 변경**: 업무명/종류 → 사건번호 / 사건명 / 다음 기일(D-n 형태)
3. **입력 예시 문구 변경**: "2026가단54321 어디까지 했지? 이번주 뭐부터 해야 하지?" 등 변호사 재개 맥락
4. **비밀유지 문구 추가**: 입력창 근처 배치
5. **데모 라우팅**: 칩(버튼) 기본 + 데모용 사건번호 입력 시 자동 연결, 미일치 시 안내 (빈 화면 방지)

### ❌ 제외하는 것
- 커넥터 실연동 기본화 (데모 영상 촬영용으로만)
- 파일 업로드 (작업량 증가)
- 히스토리 누적 (지난 카드 쌓아두고 비교)
- OAuth/계정 연결 (대회 심사 외 타인 계정/API 연결 없음)
- 판정 로직 변경 (상태 판정·충돌 판정·근거 표시은 예선 스킬 규칙 유지)

### 프론트 변경 (index.html)
- DEMO 배열 → 변호사 사건 3건으로 교체 (사건번호/사건명/기일 포함)
- MABC 2027 pills 제거 또는 변호사 맥락으로 변경
- 입력창 placeholder 예시 문구 변경
- 결과 카드 헤더 렌더링 수정 (사건번호, 사건명, 다음 기일 D-n 추가)
- 비밀유지 문구 추가 (input-card 내부 하단)
- 데모 라우팅 로직 수정:
  - demo-pick-btn 클릭 시 해당 사건번호/질문으로 입력 채우고 runGenerate(isDemo=true)
  - 입력창에 데모용 사건번호 포함 시 자동 데모 경로
  - 미일치 시 안내 + 데모 칩 재유도
- 카드 렌더링에서 출처/근거 펼침 구조 확인 (기존 reason 펼침 유지, 출처 표시 강화)

### 백엔드 변경 (api/generate.js)
- buildDemoResult의 demoMap → 변호사 3건으로 교체
- 데모용 사건번호 매핑 로직 추가
- 응답 구조에 사건번호·사건명·다음 기일·D-n 포함 확인
- 판정 로직 건드리지 않음

### 백엔드 변경 (api/debug-demo.js)
- generate.js와 일관성 유지 위해 동일하게 교체

## 4. 데모 라우팅 설계

### 방식: 하이브리드
1. **데모 칩(버튼) 클릭** → 해당 사건의 질문/사건번호로 입력 채우고 runGenerate(isDemo=true)
2. **입력창에 데모용 사건번호 포함** → 해당 사건으로 자동 라우팅 (isDemo=true 처리)
3. **미일치 입력** → 안내 메시지 + 데모 칩 재유도 (빈 화면 방지)

## 6. 심사 답변 준비 (추후)

- "AI가 법률 판단을 대신하나?" → 아님, 업무 재개 맥락 정리 도구
- "추정 안 한다면서 어떻게 첫 행동을 정하나?" → 있는 조각 기준, 출처 함께 제시
- "데이터는 어떻게 다루나?" → 요청 단위 처리, 서버 저장 없음
- "왜 이 직군인가?" → 재개 패턴이 업무 리듬에 붙고, 재개 마찰 비용이 큰 직군
- "실제 전자소송 연동되나?" → 데모 영상용 별도, 배포본 기본값은 데모 데이터
