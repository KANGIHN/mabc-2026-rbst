# 서비스 MVP 초안 — work-resume 기반 (업무 재개 카드)

> 이 파일은 서비스 MVP 설계를 1~10 항목으로 정리한 초안이다.
> 확정 전 확인 필요 항목은 10번에 분리해 둔다.

---

## 1. 문제 정의 (서비스 관점 재정리)

- **핵심 불편**: 복귀·전환·토스·인수인계·휴가 복귀·프로젝트 전환 등에서, 흩어진 기록(메모·회의록·메일·메신저·투두·작업일지 등)을 다시 훑어야 다음 행동을 잡을 수 있는 구조. 그 기록을 찾는 것 자체가 번거롭고, 찾는 동안 시야가 흐려짐.
- **직접 입력방식으로 해결할 수 없는 부분**:
  - 사용자가 기록할 곳을 기억해서 매번 찾아 넣어야 함 → 번거로움
  - 기록이 여러 곳에 쌓이면 어느 것이 최신인지 판단이 어려워짐
  - 최신 기록을 못 믿으면 재사용하지 않게 됨 → 결국 서비스를 안 쓰게 됨
- **그래서**: 서비스는 **"이어가고 싶은 일 하나"**만 묻고, 그 단서로 연결된 도구·MCP에서 관련 기록을 스스로 찾아 모으는 구조. 사용자는 기록을 찾아다니지 않고, 결과(카드)만 확인한다.
- **충돌 처리 관점**: 기록이 여러 곳에 쌓이면 어느 것이 최신인지 판단이 어려워지는데, 서비스가 충돌 지점을 찾아 보여주면 확인할 대상이 좁혀진다. 하나로 덮어 판단하지 않고 모두 보여준다.

---

## 2. MVP 핵심 가치

- **핵심 가치(한 문장)**: "어디까지 했더라" 고민을 5분 안에 끝낸다.
- **존재하는 이유**: 재개할 때 흩어진 기록을 다시 읽지 않아도 되게 하는 것. "완벽하게 재개"가 아니라 **5분 만에 이어서 보기**가 가능하게 하는 것.

---

## 3. MVP 범위 (포함 / 제외)

### 포함 (MVP) — 기능 단위로 P0/P1 구분

**P0 (결선 데모에서 핵심이 보여야 하는 것)**
1. **입력**: 이어가고 싶은 일 하나(질문형/태그·키워드형). 필요하면 최근 한 줄 메모·기록 요약·토스 맥락 단서(선택)
2. **기록 탐색·수집(서비스 주도)**: 연결된 도구·MCP(메일·캘린더·메모 등)로 관련 기록 탐색. 연결 환경이 아닌 경우를 위한 보충 경로 유지
3. **업무별 카드 생성**: 현재 상태 → 첫 행동 → 주의사항 + 근거(핵심 1줄 우선, 필요 시 상세)
4. **충돌·비확실성 처리**: 충돌은 모두 표시 + 확인 필요, 확정적 종료 표현만 완료로, 애매하면 확인 필요
5. **다중 업무 처리(최우선 1장 출력)**: 여러 업무가 식별되면 그중에서 **가장 우선시되어야 하는 업무 카드 1장**을 먼저 출력. 나머지 업무는 요약·목록 수준으로 간략히 안내하거나 후속 단계로 넘김
6. **체험(데모) 경로 추가**: 연결/연동/계정 환경이 아니어도 핵심 카드 생성 로직(상태 판정 → 첫 행동 → 주의사항 + 충돌·근거 처리)이 실제로 진행되는 흐름이 보이도록 하는 최소 경로 확보. **단, 데모 경로가 핵심 로직을 우회해 단순히 예시 카드만 보여주는 구조는 지양**

**P1 (있으면 좋지만 당장 아닌 것)**
- 태그/키워드 기능이 입력 보조로 자연스럽게 들어가는 정도, 태그 추천 자동화는 제외
- 결과 화면에서 상세 근거 펼침, 핵심 근거 우선 노출 등 UX 다듬기
- 진입 문구("무엇을 꼭 완벽하게 재개할 필요 없이, 5분만 이어서 보기")를 필요한 곳에 얇게 사용

### 제외 (당장은 빼되, 이유 명시)
- 저장소 자동 연동 전체 → 지금은 연결 가능한 범위에서만, 자동 연동 전체는 아님
- 히스토리 누적·관리 → 이번엔 한 건 재개 카드 생성이 중심
- 토스·인계용 별도 포맷, 교대·인수인계 템플릿 → 이번엔 일반화보다 핵심 카드 생성이 우선

## 4. 입력 설계 (서비스 주도 구조)

### 4-1. 입력 두 갈래
- **질문형**: 예: "A 프로젝트 자료 정리 어디까지 했지?", "B팀 답변 기다리는 거 지금 어디쯤이야?"
- **태그/키워드형**: 예: "A 프로젝트", "분기 검토", "B팀 답변 대기"
- 둘 다 **"이어가고 싶은 일 하나"**를 특정하게 하는 목적. 입력은 짧게.

### 4-2. 입력이 담아야 할 것 (최소)
- 재개하려는 업무/프로젝트 힌트(이름·단서·키워드·질문)
- 필요하면 최근 한 줄 메모/기록 요약 붙여넣기(보충용, 필수 아님)
- "누구한테 토스" 같은 맥락 단서(선택)

### 4-3. 입력이 담지 않아도 되는 것
- 여러 곳에 흩어진 기록을 사용자가 직접 찾아 넣기
- 기록 원문 전체 붙여넣기(필수 아님, 서비스 환경에서 가져올 수 있으면 가져오도록)
- 매번 최신 기록을 사용자가 판단

### 4-4. 예시 문구 (수정: 시간 특정 표현 제거)
- placeholder: "이어가고 싶은 일을 질문이나 태그/키워드로 알려줘"
- 예시 노출: "A 프로젝트 어디까지 했지?", "분기 검토", "B팀 답변 대기"
- 시간 특정 표현(어제, 지난주, 아침에 등)은 예시에서 제외. 기능은 유지하되, 예시 문구는 심사관이 별도 기록을 준비하지 않아도 이해할 수 있는 형태로.

### 4-5. 기록이 없을 때 안내 (수정: 톤·중립, 데모 경로 연결)
- 연결된 도구에서 관련 기록을 찾지 못했을 때: "연결된 도구에서 관련 기록을 찾지 못했어요." 정도 중립 안내
- 이어서 두 갈래 중 하나로 연결:
  - 보충 입력 유도: "최근 메모·요약·키워드를 알려주시면 그 기준으로 잡아볼게요."
  - 데모 예시 이어짐: "데모 예시로 진행 상황을 보고 싶으신가요?" (실제 로직이 돌아가는 예시 입력 → 실제 카드 출력)
- "분석할 기록이 없다"는 표현은 톤이 차갑게 느껴질 수 있어, 중립·도움 톤으로 조정. **데모 기록 보기는 단순 예시 카드 노출이 아니라, 실제 카드 생성 흐름(상태 판정 → 첫 행동 → 주의사항 + 근거는 실제 로직으로)이 보이는 구조**여야 함. 이렇게 하면 3번의 체험(데모) 경로와 자연스럽게 연결됨.

## 5. 서비스 흐름 (첫 화면 → 결과)

### 5-1. 첫 화면
- 상단: 서비스명 + 한 줄 설명
- 메인: 짧은 입력 필드 하나
  - placeholder + 예시 문구 2~3개 노출
- 버튼: **'카드 생성'** 같은 단추로 표시 (질문형이면 바로 처리)
- 선택 요소(얇게): 태그/키워드 언급이 있으면 관련 업무로 좁힘(필수 아님)
- **심사용 데모(체험) 기능 표현**:
  - 첫 화면에 "데모 예시로 체험하기" 같은 보조 버튼/링크(작게, 입력창 근처)를 두어 심사관이 바로 핵심 흐름을 확인할 수 있게 함
  - 다만 너무 튀거나 "이게 주력 기능인가?" 싶게 보이지 않게, 보조 위치·표현으로 둠
- **관련 기록 숫자 표시**:
  - 실제 기록 찾기 모드에서만 노출 (예: "관련 기록 2건 찾음")
  - 데모/기록 없음 상황과는 구분 (이때는 "기록을 찾지 못했어요" 상태나 데모 모드로 자연스럽게 넘어가게 처리)
  - 개수만 보여주고 내용은 카드에서 필요한 범위로 분리 (민감·개인정보와 연결되지 않도록)

### 5-2. 처리 흐름
1. 사용자 입력 수신(질문형/태그형/메모 보충)
2. 서비스가 연결된 도구·MCP에서 관련 기록 탐색  
   - 연결 범위가 아니면 사용자가 이 대화/화면에서 준 요약·메모·키워드를 기준으로 동작
3. **처리 중 상태 표시**:
   - "기록을 찾고 있어요…" 문구 + progress bar
   - 버튼 비활성화
4. 결과 출력
   - 업무별 카드(현재 상태 → 첫 행동 → 주의사항)
   - 근거(핵심 1줄 우선, 필요 시 펼침 상세)
   - 충돌/확인 필요는 그대로 표시, 하나로 덮지 않음
   - 상한(우선 1장) 초과 시 주요 카드 1장 + 그 외 요약/목록

### 5-3. 결과 화면 구성(카드 예시)
- 업무명/종류 상단
- 현재 상태(라벨 가능)
- 첫 행동 1개 + 근거 1줄
- 주의사항(기한/리스크/대기/충돌/토스·인계 포인트)
- **근거 토글 스위치(펼치기/접기) 아이디어 반영**:
  - 기본: 각 항목마다 핵심 근거 1줄씩
  - 펼치면: 상세 근거(참고 범위, 기록·출처 등)
  - 근거가 동일하면 그대로, 다르면 각각 표기 (첫 행동과 주의사항 근거가 다를 수 있으므로)
- **카드 하단 "다른 업무 이어하기/보기"**:
  - MVP에서는 기본 출력이 가장 우선시되는 업무 카드 1장이니까 항상 필요하진 않음
  - 다만 여러 업무가 식별될 때 "그 외 ○○건 더 있음" + "다른 업무 보기" 연결점이 있으면 흐름상 자연스러움
  - MVP에서는 요약·목록 안내 + 필요하면 다른 업무 보기 연결 정도로 두면 무난

### 5-4. 기록 없음과 작업 실패 구분
- **기록 없음**: 서비스 로직은 정상 동작했지만, 찾을 수 있는 관련 기록이 없는 상태
  - 안내: "연결된 도구에서 관련 기록을 찾지 못했어요." + 보충 입력/데모 제안
- **작업 실패**: 서비스 처리 중 에러, MCP 호출 실패, 타임아웃 등 로직 진행이 멈춘 상태
  - 안내: "기록을 불러오는 중 문제가 있었어요. 잠시 후 다시 시도해 주세요."
- 둘을 화면에 다른 문구와 처리로 명확히 구분 (내부 실패 유형 구분은 필요하나 사용자에게는 두 상태를 다르게 보여주기)

## 6. 처리 상세 로직 (서비스 로직 관점)

### 6-1. 업무 구분 — 명확히 카테고리화
- 일반 진행 업무 / 검토·의사결정 대기 업무 / 기한형 업무 / 토스·인계 대상 업무 등으로 구분
- 애매하면 가장 가까운 유형으로 임시 분류 + "(분류 확인 필요)"
- **데모용도 심사 한정 추가 검토**:
  - 별도 카테고리를 신설하기보다, 데모 시나리오용 예시 입력/예시 업무로 처리하는 쪽이 서비스 로직과의 괴리가 적음

### 6-2. 대기 처리 — 수정 반영
- 기다리는 항목(내용, 마감일)을 중요/주의사항에 표기
- 이 내용이 없으면 **확인 필요**로 표기
- 예: "답변 대기 중(누구로부터 오는지 불명확) — 확인 필요"

### 6-3. 첫 행동 제시 + 근거 (기존 안 그대로)
- 업무마다 지금 바로 할 일을 하나 뽑고, 그 근거를 함께 표시
- 착수 가능하면 첫 행동 1개 + 근거(관련 기록/마지막 업무의 출처, 어떤 내용을 보고 제안했는지)
- 마감이 아직 멀고 진행만 유지하면 되는 상태면 "진행 유지, 당장 착수할 일 없음(기한 전)"으로 명시하고 근거도 함께 정리

### 6-4. 충돌 발생 시 첫 행동 — 수정 반영
- 충돌 시 첫 행동은 **"무엇을 어디서 확인/행동할지"** 형식으로 제시
- 예:
  - "메모 vs 메일 상태가 달라요. 최신 상태를 확인하려면 해당 메일 스레드 또는 담당자 기준으로 먼저 확인해 주세요."
  - "기록 A가 '거의 끝남', 기록 B가 '검토 중'이면, 먼저 [기록 B 담당자]에게 현재 상태를 문의한 뒤 재개하세요."
  - 담당자를 알 수 있으면 "담당자에게 확인", 없으면 "어느 쪽 기록이 최신인지 확인"으로 구분

### 6-5. 마감·리스크 (기존 안 그대로, 같이 포함)
- 기한/마감, 지연 시 영향, 끊기면 안 되는 연결 포인트, 대기 중인 것 등을 주의사항에 모음
- 리스크(지연 시 영향, 끊기면 안 되는 연결 포인트 등)가 있으면 함께 적는다.

## 7. 사용성 중심 원칙 (검토 + 반영)

- **입력은 짧게, 출력은 명확**: 사용자는 업무 하나만 말함 → 서비스는 카드 출력
- **기록 수집은 서비스 몫**: 사용자가 기록을 찾아 넣지 않음
- **확실하지 않으면 확정처럼 말하지 않음**: 추정/확인 필요 구분 (아래 7-3 반영)
- **충돌은 숨기지 않음**: 모두 보여주고 확인 필요로 표시
- **민감 정보는 초기버전 기준 별도 처리 (아래 7-5 반영)**
- **한 장 카드 원칙 유지**: 업무별 카드, 같은 순서/제목
- **사용이 어려운 사람도 첫 화면에서 무엇을 하는지 알기 쉽게**: 입력 필드·예시 문구·버튼이 스스로 설명하게

### 7-3. 추정/사실/확인 필요 태그 — 검토 결과 반영
- 기존에 "추정하지 않는다"는 원칙을 뒀지만, **사용성 관점에서 보면 추정이 아예 없는 것보다, 합리적으로 추정할 수 있을 때 [추정]으로 명시하는 편이 더 유용**할 수 있음
- **조건**: 기록을 조합해서 합리적으로 추정할 수 있는 경우에만 [추정] 태그를 달고 카드에 표기
- **핵심**: [추정]은 "기록을 근거로 합리적으로 보이지만 확정은 아닌 것"이지, "없는 내용을 지어내는 것"이 아님. 따라서 원래의 "추정인데 사실처럼 단정하지 않는다" 원칙은 유지되고, 다만 **합리적 추정이 가능하면 금지하지 않고 라벨로 구분**하는 쪽으로 조정
- 사실/추정/확인 필요 3구분은 그대로 유지, 사용자는 "어디까지가 확정이고 어디부터 추정인지"를 볼 수 있게 됨
- **검토 결과**: 7-3 방향 찬성. "추정 금지"에서 "합리적 추정 가능 시 [추정] 표기"로 조정하되, 근거 없는 과추정은 여전히 금지

### 7-5. 민감정보 범위 — 초기버전 기준 명확화 (수정 반영)
- 초기 버전에서는 **이름, 연락처, 메일주소**만 공개 대상(업무상 필요한 개인 특정 정보)으로 두고, 나머지는 민감정보로 보고 출력 제외
- 출력 제외된 경우 **"민감정보로 출력하지 않음"**을 밝힌다
- 단, 이름/연락처/메일주소도 무조건 전부 노출하는 게 아니라, **토스·인계·담당 확인 등 업무상 필요한 맥락에서 필요한 범위만** 표시한다. 불필요하게 나열하지 않음
- **검토 결과**: 7-5 방향 찬성. MVP 초기에는 경계를 이름/연락처/메일주소로 좁혀 두고, 출력 제외 시 민감정보 처리임을 명시하는 식으로 정리하면 심사/데모에서도 설명 가능하고, 실제 사용 맥락(토스·인계에서는 오히려 필요 정보)과도 충돌하지 않음

## 8. 기록 접근 방식 (MVP 기준)

- **기본 원칙**: 서비스가 도구·MCP로 관련 기록을 찾는 구조 (사용자는 직접 찾아 넣지 않음)
- **MVP에서는 꼭 필요한 기록 접근 경로만** 추리고, 나머지는 연결 가능한 범위에서 확장 후보로 둠
- **MCP 연결 없는 환경/심사 현실 대응**: 보충 경로(사용자 제공 메모·키워드) + 체험(데모) 경로 확보
- **체험(데모) 경로**:
  - 예시 데이터로 핵심 로직(상태 판정 → 첫 행동 → 주의사항 + 근거, 충돌 처리)이 실제로 돌아가는 흐름을 보여줌
  - 단순 정적 예시 카드 노출은 지양
  - 데모 데이터면 예시 표지와 함께 (사용자가 헷갈리지 않게)
- **가상 데이터/데모 데이터 활용**: 필요. 다만 실제 연동 환경 로직과 데모 경로용 예시 데이터는 분리해 생각
  - 기본 로직은 실제 기록 출처를 기준으로 동작, 데모/체험 경로에서 예시 데이터로 흐름 보여줌
- **검토 결과**:
  - MVP에서 MCP를 아예 빼는 것보다, **최소한의 기록 출처 경로 + 데모 경로로 심사 현실 대응**이 더 나은 방향
  - 가상 데이터는 데모 경로에서 핵심 흐름이 보이게 할 수 있으면 충분히 가치 있음
- **확인 필요(PRD/배포 단계에서 정리)**:
  - 실제 서비스 환경에서 연결 가능한 도구·MCP 범위
  - 심사 시점에 실제 MCP 연동이 가능한지/불가능하다면 어떤 환경으로 보일지
  - 데모 데이터 예시 기록의 구성 수준 (몇 건, 어떤 상태 분포로 보일지)

## 9. MVP로 "이 서비스를 왜 계속 쓰게 되는지"

- **핵심 가치 문장**: "어디까지 했더라" 고민을 5분 안에 끝낸다.
- **재개 진입 장벽 낮춘다**: 서비스는 **"관련 모든 기록을 찾지 않아도, 찾은 것만으로 재개 진입 장벽을 낮춘다"**는 가치
  - 기록이 확실치 않으면 사용자가 직접 봐야 할 수도 있지만, 그때도 "무엇을 어디서 확인"까지는 서비스가 안내 (6-4 충돌 처리 등)
  - "찾은 것만으로도 다음 행동을 바로 잡을 수 있게 해주는 것"이 핵심
- **반복 사용 맥락**:
  - 출근 직후, 휴가 복귀, 프로젝트 전환, 토스·인계, 일주일 만의 재개 등에서 자연스럽게 필요해지는 서비스
  - 매번 흩어져 있던 기록을 다시 읽지 않고, 이어갈 일만 말하면 카드가 나온다는 일관된 경험
- **MVP에서 표현하는 방식**:
  - 진입 문구/예시: "출근해서 바로 다음 할 일 보여줘", "일주일 만에 이어서 하려고 하는데", "어제 하던 거 이어서 할게" 등 (단, 예시 문구는 심사 현실 고려해 시간 특정 표현 제외 가능 — 예: "A 프로젝트 어디까지 했지?", "분기 검토")
  - 데모 시나리오: "복귀 상황" 같은 반복 맥락을 하나 넣어두면 설득력↑
- **예선 스킬 활용도 연결 (30점 블록)**:
  - work-resume의 핵심 로직(상태 판정 → 첫 행동 → 주의사항 + 충돌/근거 처리)이 서비스에서 그대로 살아 있고, 반복 사용 상황에서 그 로직이 계속 동작한다는 점
- **9-1·9-6 반영 완료**

## 10. 확인 필요 (최종 기반 수정)

### 10-1. 서비스 환경과 연동 범위
- 서비스와 연동할 도구·MCP 실제 범위 (메일/캘린더/메모/메신저 중 어디까지 연결 가능한지)
- 내부 대화/기록 참고를 서비스 MVP에 넣어도 되는지 (존재·접근 권한·개인정보 포함 여부 실제 환경 확인 필요)

### 10-2. 심사 시 로그인/MCP 연동 없이 테스트
- 서비스 환경에서 도구·MCP 연동이 실제로 어디까지 가능한지 (미확정)
- 심사 시점에 서비스 상태가 연동 O/X 중 어떤 환경으로 보일지 (미확정)
- MVP에서 "연동 없이도 핵심 카드가 나오는 최소 경로"를 어디까지 넣을지:
  - 보충 경로(사용자 제공 메모/키워드)만으로 충분할지
  - 체험(데모) 경로에서 예시 데이터로 실제 흐름을 보여주는 것으로 충분할지
  - 둘 다 필요한지
  → **PRD에서 정리**

### 10-3. UX/인터페이스 구성 방향 (멘토링 확인 항목 삭제, PRD/배포 단계 확인)
- 예선 스킬 서비스화 시 UX/인터페이스 변경 허용 범위 — **PRD/배포 단계에서 확인 필요**
- 첫 화면 버튼·데모 표현·관련 기록 숫자 표시 등 실제 화면 구성 방향
- "카드 생성" 버튼, 데모 체험 버튼 위치·표현, 관련 기록 숫자 노출 조건 등

### 10-4. 다중 업무 처리 세부
- 우선 1장 출력 + 나머지 요약/목록 구성 수준 (예: "그 외 ○○건 더 있음" + "다른 업무 보기" 연결 포함 여부)
- 다중 업무 식별 시 우선순위 기준 (재개 맥락과 관련도 높은 업무 우선 등)

### 10-5. 민감정보 범위·출력 제외 표시
- 초기버전 민감정보 경계(이름/연락처/메일주소)까지로 실제로 충분한지
- 출력 제외 시 "민감정보로 출력하지 않음"을 어느 수준에서 밝힐지 (카드 내 명시, 별도 안내 등)

### 10-6. 데모 경로·데모 데이터 구성
- 체험(데모) 경로에서 예시 데이터 구성 수준 (몇 건, 어떤 상태 분포, 충돌/대기/마감 포함 여부)
- 데모 데이터 사용 시 예시 표지 방식 ("데모 예시", "예시 기록" 등)
- 데모 경로가 심사용 따로인지, 실제 서비스 체험 경로 겸용인지

### 10-7. 제출물 관련 미확정 (별도)
- 제출 폼 양식 (추후 공지) — 미확정
- 포스터 템플릿 (차주 초 전달 예정) — 미확정
- 발표 템플릿 실제 파일 링크 — 링크만 확보, 아직 확인 안 함
- OT/결선 교육 다시보기 (bit.ly/mabc2026-final-ot) — 아직 확인 안 함
- 오픈소스/외부 라이브러리 사용 내역·출처 정리 범위 — 요청 시 대응 가능하게 준비

### 10-8. 개발 기록·검증 관련 (규정 연결)
- 제10조 개발 기록 검증: Timely 내 대화·입출력 기록과 PRD·소스코드 정합성 대비 가능해야 함
- 서비스 MVP에서 "어떤 기록이 어디서 왔고, 어떤 근거로 판단했는지"가 설명 가능하게 정리되어야 함
- 외부 데이터 활용 시 저작권·출처 표기, 타인 저작물·동의 없는 개인정보 미포함 — 서비스에서도 그대로 적용
