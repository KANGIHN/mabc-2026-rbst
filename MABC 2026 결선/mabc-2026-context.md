# MABC 2026 결선 준비 컨텍스트 (A 수준 요약)

이 파일은 새 세션에서 이어서 작업할 때, 내가 대회 규정 범위 안에서만 움직이도록 붙잡는 기준 파일이다.
새 세션이 열리면 이 파일을 먼저 읽고, 규정/내 방향이 아닌 얘기는 범위에서 벗어난 것으로 본다.

## 1. 대회 기본 뼈대

- 대회: MABC 2026 (Making AI Beneficial 챌린지) 결선
- 테마/슬로건: Skill to Service — 나만의 스킬에서 모두가 쓰는 서비스 MVP로
- 핵심 일정:
  - 09/09(수) 20:00: 결선 OT & 라이브 교육 (유튜브 라이브)
  - 09/10(목) ~ 09/15(화): 전문가 1:1 밀착 멘토링 (온라인, 디스코드)
  - 09/16(수) 18:00 KST: 결선 최종 산출물 제출 마감 (마감 후 수정 불가)
  - 09/19(토) 11:00~17:00: 최종 발표회 및 시상식 (@ 한국과학기술회관)
- 발표 형식: 2부 최종 피칭, 발표 8분 + Q&A 3분
- 포스터 피칭: 1부 포스터 피칭 (A1 세로 1장, 3분 피칭)

## 2. 참가 전제 (네 선택)

- 참가 형태: 개인 참가
- 개발 플랫폼: 타임리(Timely AI)만 사용
- 배포: Vercel로 독립 배포
- 예선 대표 스킬: work-resume (업무 재개 카드)
- Hermes Agent는 사용하지 않음

## 3. 포함하려는 상황/환경 (문제 정의 방향)

- 예선 스킬을 제출하고 결선 진출 사실을 알았을 때, 내가 만든 스킬이 정확히 뭐였는지 바로 기억나지 않아 기억을 더듬은 경험
- 이 경험을 살려, 복귀·전환·토스·프로젝트 전환 상황에서 "흩어진 기록을 다시 훑지 않으면 다음 행동을 못 잡는 불편"을 문제 정의로 연결
- 단, 이 경험은 개인 경험에 머무르지 않게, 보편적인 불편과 연결해서 일반화할 것

## 4. 제출물 5종 (결선 과제 제출 가이드 기준)

1. 서비스 MVP URL & 소스코드
   - 독립 배포 공개 URL (Vercel 권장, 타 플랫폼 가능)
   - 소스코드 저장소 링크 (GitHub 등, 공개(Public) 필수)
   - 배포본 식별 정보(커밋 해시 등) 함께 기재
2. PRD (개발 명세서)
   - PDF 또는 Markdown, 2쪽 내외
   - Skill-to-Service 미니 PRD
3. 포스터
   - A1 세로 1장 (PDF)
   - 제공 템플릿 필수 (현재 미전달, 추후 공지)
4. 발표자료
   - PDF (5장 이내)
   - 제공 템플릿, Noto Sans 폰트 필수
   - 편집파일 금지 (PDF로 변환 제출)
5. 데모 영상
   - 3분 이내 MP4 (실제 동작 화면)
   - 사전심사 / 현장 백업용

## 5. 점수 구조 (심사 기준 및 평가 가이드 기준)

총 100점 = 사전 심사 90점 + 현장 발표 10점

- Project Impact (문제 정의·기획): 25점
  - 문제 정의가 타당하고 실용적이며, 그에 맞는 기획이 이루어졌는가
- 예선 스킬 활용도: 30점 (최대 블록)
  - 예선 대표 스킬이 서비스에서 중심 역할을 하며 안정적으로 동작하는가
- Technical Implementation (사용성): 15점
  - 처음 방문한 사람도 직관적으로 쓰고, 핵심 기능이 목적에 맞게 동작하는가
- Innovation & Creativity (독창성·확장성): 20점
  - 서비스 사용 전후 효과가 뚜렷하고 문제 해결 방식이 새로운가
- 발표 전달력·논리: 10점 (현장 발표)

평가 방침:
- 완성도는 심미성이 아니라 사용성(핵심 기능의 명확한 동작, 이해 가능한 화면 구성) 관점
- 개발 플랫폼 차이로 인한 유·불리 없음
- 동점 시 먼저 제출을 완료한 팀에 우선순위

## 6. 하지 말아야 할 것 (빨간선)

- 외부 LLM(Claude·GPT·Gemini 등)을 직접 호출해 서비스에 사용 → 실격
- Claude Code·Cursor·Codex 등 외부 AI 코딩 에이전트·어시스턴트를 개발 과정에 사용 → 부정행위
- 타임리 워크스페이스 공유 링크를 배포 URL로 제출 → 불인정
- API 키·토큰을 소스코드/PRD/서비스 UI에 노출 → 본인 책임
- GitHub 레포를 Public이 아니게 제출 → 요건 미충족
- 로컬/타임리 내부에서만 동작하는 URL을 배포 링크로 제출
- 발표자료를 편집파일 형태로 제출 (PDF 변환 필수)
- 포스터를 제공 템플릿 없이 만들거나 A1 세로 1장 규격 위반
- 마감(9/16 18:00) 이후 제출·수정
- 9/19 현장 발표에 팀원 중 1인 미참석 (팀일 경우; 개인이면 본인 참석)
- 플랫폼 선택을 09/9 이후 변경하려고 시도
- 크레딧 소진 후 추가 지급 기대 → 불가
- 타인 스킬 무단 사용, 도용·표절
- 타인 저작물·상표 무단 사용, 타인 개인정보 동의 없이 포함·노출
- 유해/차별·혐오·폭력·음란 등 공서양속 위반 콘텐츠
- 오픈소스·외부 라이브러리 라이선스 미준수 (요청 시 출처 밝혀야 함)
- 운영진의 재현·검증 요청(소스코드 제공, 시연, 기록 확인 등)에 불응

## 7. 허용/유의 가능한 것

- MCP 활용 허용 (외부 데이터 활용 시 저작권 표기 필수, 타 LLM 활용한 합성데이터 제작은 불가)
- 공개 외부 API(공공데이터·지도·날씨 등) 사용 허용 (제5조 제3항)
- 코드 편집기로 직접 작성·수정 허용 (단, 제10조 검증 과정에서 설명 가능해야 함)
- 예선 스킬을 서비스화할 때 수정·확장은 허용 (단, 핵심 로직으로 남아야 함)
- fallback 예외: 플랫폼에서 이미지 등 입력 시, 타 LLM 제외 fallback 활용은 허용

## 8. 타임리 전용일 때 특히 중요한 점

- 개발 기록 검증(제10조)은 타임리 내 대화·입출력 기록 기준으로 이뤄짐
- 제출 PRD·소스코드와 타임리 기록을 대조해서 정합성을 봄
- 개발 기록으로 설명되지 않는 코드·기능이 있으면 규정 외 도구·모델 사용으로 추정 → 소명 필요
- 즉, "타임리 안에서 뭘 했는지"를 PRD·코드와 연결 지어 설명 가능하게 정리해두는 게 안전
- Hermes 미사용이므로 "Hermes 데이터 적재 동의"는 해당 없음
